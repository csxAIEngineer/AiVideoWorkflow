## 目标

编剧先定故事、人物动机、因果和情绪基调。资产、分镜、动作引擎和投喂只在这份已确认剧本上增强表达。要改剧情，退回编剧确认。质检按职责把问题送回责任阶段，不替别的阶段改稿。

保留现在的阶段串行、LangGraph 写稿图、以及 End 的生成执行链。不重写 12 个技能，不建六区共享稿件或并发补丁系统，不碰 ComfyUI。

## 1. 现在的流程和目标差在哪

锁定机走 `end/stage_runner.py` 的 `execute`：一次只写当前阶段，停在门上。`end/server.py` 的 `run_project_gated` 再决定重写或进入下一段。顺序是对标（有则先做）然后剧本、资产、分镜、投喂。没开锁定机时，`_run_project` 用 `WRITE_STAGES` 把 P1 到 P4 各整段写一遍。两条路都是整段覆盖后存盘。

写稿图在 `AI/qwen_api/suite_graph.py`：同一阶段的原文按 `AI/skills/registry.py` 的 `pack_cohorts` 分成几路模型调用，再由一个汇总节点写成该阶段整份 JSON。机检失败项走 `AI/qwen_api/repair_graph.py`，汇总节点只按编号收集文本，拼回在 `end/repair_units.py`。出片在 `end/render_loop.py`，不进这张写稿图。

Front、End、AI 仍是目录之间的 JSON-RPC。

- 职责边界主要写在技能正文和阶段简报里。第一次写资产、分镜、投喂时，上一阶段正文只是「上一阶段正文：」，锁定参考那句只出现在返修简报。汇总节点仍是一次模型调用，按 `registry._MERGE_SHAPE` 交出整段稿。提示词要求保留，代码不核对保留了没有。
- 剧本「确认」只是 `pipeline.accepted` 里有 `script`，以及用户点过继续。没有剧本正文哈希，没有确认版本号。下游产物不记录自己依据的是哪一版剧本。
- 质检的「路由回责任阶段」停在技能原文。代码里的独立质检默认关闭（`advisory_qc_enabled`，846–851 行）。打开时也只是旁路写 `质检.md`。汇总形状写着不要改写剧本、资产、分镜或投喂稿（`registry.py` 的 `qc` 形状）。真正的门失败会在当前阶段就地返修：资产、分镜、投喂走 `repair_graph`，剧本失败仍停在剧本门。没有按「这是剧情问题所以退回编剧」分类。
- 分镜技能写明无权删改台词，只能出「台词精简建议清单」等用户点头（`sd-storyboard-engine/SKILL.md` 第 31 条）。投喂技能写明缺台词要回退上游，不得在本层消化。End 没有调用 `script_feed_diff.py`。机检报告里的台词问题会在分镜或投喂阶段就地改，不会退回剧本确认。
- 动作引擎是分镜和投喂阶段的 cohort，不是单独阶段。`slice_context.resolve_files` 在 P3/P4 且动作档为 R1/R2/R3 时挂上 real、combat 或 xuanhuan。打斗范文要求按当次剧本现写。没有代码阻止动作稿增加剧本里没有的胜负、人物或结局。
- 画布可以改单块提示词。`end/revise.py` 里剧本和分镜走整段 suite，资产和镜头走单块图。保存只写文字。`save_project_content` 不作废成片，也不检查是否改了剧情。从剧本重跑会清下游；从分镜、资产或镜头重跑只作废对应出片步骤，不要求回到编剧。
- 单块守卫能发现新增的 `图N`、`A/P/U` 号和镜头引用。它不能发现同一批编号里换了动机、因果或台词。

### 缺失

- 没有「已确认剧本」这个系统对象。确认后的正文、版本和确认时间没有单独落下。后续任何写者都可以改掉 `spec.script` 或下游正文，而不经过剧本门。
- 没有跨阶段的剧情权检查。结构检查（图号、投喂标题、六问、H3 六段）通过，不表示人物动机、因果和情绪基调还在。
- 没有「下游想改剧情就升级到编剧」的执行路径。就地返修、画布保存、单块 revise、retouch、未开锁定机的 `WRITE_STAGES`，都不会因为语义越界而停到剧本门。
- 质检不会按归属改路由。格式问题、资产问题和剧情问题现在共用「重写当前阶段」。
- `script_feed_diff.py` 未接入 End。技能里的回退上游没有对应的代码动作。
- 旧项目没有确认版本。不能假设磁盘上的剧本已经被人确认过。

## 2. 只改提示词，和必须用代码卡住

### 只适合放进提示词

这些是模型写作时的职责说明。放进现有阶段简报即可，不必改 12 个技能文件。

- 资产、分镜、动作 cohort、投喂的首次写作简报，补上和返修简报同一句：已确认剧本整段是锁定参考。允许增加的是画面、机位、动作分解、光和声。不允许改的是人物动机、因果顺序、结局、情绪基调，以及剧本里已经写出的台词原文。
- 汇总节点的任务形状加一句：下游字段不得改写 `script`。现在资产和分镜的形状只说「用不到的字段不要写」，剧本字段如果被写出来，`_spec_patch` 在资产和分镜阶段本来就不会收 `script`。这句是提醒，不是新的存储规则。
- 质检旁路维持「只出报告、不改稿」。它已经这样写了。

局限：汇总节点一次生成整段。提示词里的「不要改」不会在落盘前被核对。模型可以换掉台词、增加人物、改掉胜负，同时仍交出格式正确的分镜或投喂。单块守卫只看编号集合。台词对照脚本如果只做 4-gram，也只能抓大段缺失，抓不住「换了一个因果相反的句子」或「动机从复仇改成和解」。结构通过、引用还在，都不能当成剧情没变。

### 必须用代码卡住

- 确认版本。剧本门用户点「继续」时，对当时的 `剧本.md` / `spec.script` 记一次版本。版本至少包含哈希、时间和来源（剧本门、画布保存、revise、重跑）。下游每次落盘带上自己依据的版本。版本不符就拒绝把下游标成最新，而不是只在提示词里提一句。
- 剧情权升级。下游写作、返修、画布保存、revise、retouch 若碰到约定的剧情信号，停止在下游落成新事实，把项目退回剧本门，附上差异说明。编剧确认后才递增版本并允许下游重写。判定先做结构规则，不做开放式语义裁判。见第 5 节的待决项。
- 按归属返修。机检或质检报告先分类，再选阶段。台词原文、人物去留、因果和结局归剧本。图块字段、外观和编号归资产。段结构、六问、机位归分镜。H3 字段、时长、图号绑定归投喂。分类失败时停在当前门并标明「未分类」，不要默认就地重写。
- 所有写入口都走同一道检查。只包住 `save_project_content` 会漏掉阶段写作。写入口见下一节。

代码也有硬边界。人名表、引号台词集合、结局句是否还在，都是表面规则。改写动机但保留原句，规则看不出来。第一期应把这种漏检写进报告，而不是声称已经证明语义没改剧情。开放式「读两段然后判断有没有改剧情」仍是一次模型调用，不能当作门禁。

## 3. 改动清单

只列准备要动的位置。本分支不实施。

### 剧本确认与版本

- `end/stage_runner.py`：`accept_pipeline` 在离开剧本阶段时写入确认版本。`_produce_script` 和剧本返修在正文变化后作废该版本，直到用户再次点继续。精修仍停在剧本门，这是现有行为，保持。
- `end/server.py`：`_save_written_spec` 把版本放进 `spec.json`，并放进 `progress`，让读接口能看见。`public_view` 现在读项目时可能重写 `spec.json`（345–362 行）。确认版本的读写不能借这次读时写入。读接口只返回版本，不在 GET 里改稿。
- 未开锁定机的 `_run_project` / `_merge_spec` 同样在剧本段落下版本。这条路径没有剧本门点击。第一期要么在写完剧本后停一次等人确认，要么明确标成「未确认，下游不得当作已锁定」。这一条等你定，见第 5 节。

### 下游引用

- `stage_brief`、`_produce` 的首次写作简报、`_repair_task`：带上确认版本号。返修路径已经有锁定参考字样，首次写作对齐它。
- `store_stage`、`_spec_patch`、`_save_written_spec`：资产、分镜、投喂落盘时记下所用的剧本版本。
- `end/rerun.py` 的 `clear_downstream`：剧本版本变化后，下游稿和出片步骤按现有重跑规则作废。现有「从剧本重跑会清下游」保持，并改成由版本变化触发，而不是只有点了重跑按钮才发生。
- 画布和成片：提示词版本和 `run_state` 的 epoch 仍是两件事。第一期不自动出片。索引或现有进度里能看出「下游稿依据的剧本版本」和「成片依据的步骤」即可。不新增六区页面。

### 越权改剧情

新增一个 End 内的纯函数，例如放在 `end/script_authority.py`（新文件，只有规则，不调模型）。输入是已确认剧本、待写入的下游文本、写入来源。输出是通过，或「退回编剧」加差异列表。

第一期规则只做能离线断言的几条：

- 从剧本抽出的台词原文（引号或「角色：」行）在下游稿里被删掉或换成另一句。
- 剧本里的角色名在下游消失，或下游出现剧本没有的角色名。角色名表来自确认剧本的固定行，不来自模型现编。
- 待写入对象本身改了 `script`，但本次动作不是剧本阶段、剧本 revise、或剧本门确认。

命中则不把下游正文写成新事实。`pipeline.current` 回到 `script`，`action` 为等待，报告里列出差异。用户在剧本门确认新正文后，版本递增，下游按现有串行链重写。

这几条抓不住动机改写、情绪基调改写、因果对调但句子还在。文档和测试名都写成结构规则，不写成语义证明。

### 按归属返修

- `end/stage_runner.py` 的 `auto_gate_action` 和 `_follow` 路径：在决定 `rewrite` 之前看报告类别。剧情类不进入当前阶段的 `repair_graph`。
- `end/repair_units.py` 的 `units_for` 保持按图块、段、投喂单元切。它只处理已经判定属于本阶段的报告。
- 质检旁路若打开，报告只落 `质检.md`。不把质检正文合并进剧本或投喂。路由仍由 End 根据报告类别改 `pipeline`，不由质检模型直接写下游。

## 4. 第一期和以后

第一期只做四件事：

1. 剧本门「继续」写下确认哈希。未确认前，下游阶段不自动开写。锁定机已经会在剧本门停下。未开锁定机的那条 `WRITE_STAGES` 要不要也停下，见待决项。
2. 共享的结构规则，接到第 3 节那张表的全部写入口。命中则退回剧本门，不就地改成新剧情。
3. 机检报告按台词原文、图块、段结构、投喂字段四类分流。只有后三类维持现在的就地返修。
4. 离线测试用假模型覆盖这四条入口里的代表路径。

第一期可以动到的前端只有现有剧本门和进度文案：退回时沿用现在的门消息，说明哪一条台词或哪一个角色名触发了退回。不新做页面。若 `projects.get` 需要带上 `script_revision` 和下游是否过期，这是现有 JSON-RPC 读模型加字段，画布可以先不画。没有这个字段之前，门消息本身就要能看懂。

以后可选，不做进第一期：

- 把 `script_feed_diff.py` 接到投喂门，基线仍先用分镜稿；与剧本台词规则并存时，以确认剧本的台词原文为准。
- 动机、因果、情绪基调的人工抽查清单，放在剧本门文案里，仍由人点，不交给质检模型自动改稿。
- 下游稿过期时在现有画布节点上显示「依据的剧本已变」。仍不做出片自动重跑。
- 动作档 cohort 的胜负句规则。等第一期台词和人名规则稳定后再定，避免和打斗范文的格式检查缠在一起。

不做六区前端，不做共享稿件协同，不做 LangGraph 重写，不改 12 个技能文件。

## 5. 验收、风险、待你决定

验收只写在测试里，用临时目录和假的 `write_model`。不调用付费接口，不部署。

场景：

- 确认剧本含角色甲和一句台词。资产假模型只加外观。期望落盘，版本相同。
- 同一剧本。分镜假模型删掉这句台词并换了一句。期望分镜文件不变，门回到剧本，选项仍是继续和精修一类的人工确认，而不是「根据建议修改」去改分镜。
- 投喂假模型让角色乙出场，剧本没有乙。期望不落盘新投喂。
- 投喂机检只报 H3 字段缺失。期望仍走现有投喂单元拼回，不退回编剧。
- 画布 `save_content` 改剧本正文。期望确认哈希失效，已有资产和分镜标成过期或按你选择的策略清掉。见下面的决定项。
- 单块镜头 revise 只改景别。期望镜头正文更新，剧本哈希不变，`revise_graph` 的标题守卫仍生效。
- 旧目录没有哈希。期望按你定的兼容策略处理，不能把空哈希当成已确认。

风险：

- 规则误伤。分镜把台词拆进镜头行、投喂把台词放进 `<d>`，表面字符串对不上就会退回编剧。规则要先规范化空白和引号，再比较。第一期宁可漏掉改写过的动机，也不要把正常的镜头拆分全部打回。误伤会让现有自动过门的资产、分镜、投喂频繁停住。
- 漏检。保留原句但颠倒因果、改掉情绪，结构规则通过。不能在界面上写成「已证明未改剧情」。
- 写入口漏接。`public_view` 的读时写、trace 回放、`WRITE_STAGES`、retouch 只要有一条没进共享函数，就越权路径还在。
- 旧项目。没有哈希时如果直接放行，等于没有这道门。如果强制全部回到剧本门，已出片的项目会被拦住。
- 确认哈希和成片 epoch 仍是两套。退回编剧不会取消已经提交的远端视频。第一期不自动作废成片，避免误删。过期要能看出来。
- Mac 上未提交的改动可能已经改了门或保存路径。远程这份计划以 `f60e9a0` 为准。落地前要先把那部分变更合进来再对写入口，不能按本文直接打补丁。

待你决定：

1. 未开锁定机的 `WRITE_STAGES` 是否也在剧本后停一次。不停的话，这条路径只能标「未确认」，不能和锁定机共用「已确认剧本」。
2. 剧情信号第一期是否只包含台词原文和角色名。动机、因果、结局、情绪基调要不要第一期就做，还是只留在提示词里。
3. 剧本一变，下游是直接 `clear_downstream`，还是先留稿并标过期，等用户在剧本门点继续后再清。
4. 旧项目没有哈希时：把当前剧本视为已确认并记下哈希，还是下次打开时停在剧本门。
5. 增强表达允不允许下游增加剧本没写的镜头动作。若允许，角色名规则不能把「剧本没写的动作描写」判成新角色。角色表要来自剧本里的人名，不来自所有名词。
6. 退回编剧时，已经生成的图和视频是保持不动只标过期，还是沿用现在的「从剧本重跑就作废下游成片」。
